# Агент ноды на сервере

Агент — единственный компонент Node Plane на VPN-сервере. Контроллер управляет сервером только через API агента по взаимному TLS. Здесь описано, что делает команда установки, как агент знакомится с контроллером и зачем ему root.

## Требования

- Linux x86_64 с systemd.
- `curl` или `wget`, `tar` и `sha256sum`.
- Debian или Ubuntu для автоматической установки Docker и инструментов ограничения скорости (`iproute2`, `nftables`, `util-linux`).
- Контроллер должен достучаться до порта агента, по умолчанию TCP 50061 (`NODE_AGENT_PORT` на контроллере). Если у провайдера свой файрвол, откройте в нём этот порт. Контроллер подключается к клиентскому адресу ноды.

## Что делает команда установки

**Установка сервера** показывает одноразовую команду; **Auto** в Workstation или **Установить по SSH** в боте могут выполнить её за вас за один SSH-вход. Команду нужно запускать от root. Она:

1. Скачивает `node-plane-agent-installer.sh` из GitHub-релиза версии контроллера и проверяет его SHA-256. Контроллер не выдаёт команду, если установщик в релизе отличается от его собственной копии.
2. Установщик скачивает архив агента того же релиза, проверяет SHA-256 из команды и устанавливает `/usr/local/bin/node-plane-agent`.
3. Ставит через `apt-get` недостающие инструменты ограничения скорости. Без них нода только сообщает, что не может ограничивать скорость.
4. Записывает `/etc/node-plane/agent.toml` и токен в `/etc/node-plane/tls/enrollment.token`. Прежние ключ и сертификат агента удаляются.
5. Если активен `ufw`, открывает порт агента.
6. Устанавливает и запускает systemd-сервис `node-plane-agent`.

Контроллер не получает ни SSH-доступа, ни SSH-ключа, ни sudo. **Auto** в Workstation входит один раз вашим ключом или паролем, использует `sudo`, если вход не под root, и ничего не сохраняет. **Установить по SSH** в боте входит один раз ключом контроллера, который вы заранее добавили на сервер, и требует root или sudo без пароля; после этого контроллер ничего не делает на этом сервере по SSH.

## Регистрация

Агент сам генерирует закрытый ключ на сервере; ключ сервер не покидает. Пока у агента нет сертификата, на его порту работает только регистрация.

Подключается всегда контроллер к агенту, а не наоборот, поэтому контроллер может стоять за NAT. Обе стороны доказывают знание токена через HMAC от данных обмена, включая открытый ключ агента. Сам токен по сети не передаётся, а посредник не может подменить ключ. Затем контроллер выпускает своим CA сертификат на ключ агента. Агент сохраняет CA и сертификат, удаляет токен, применяет правило доступа к порту и переходит на взаимный TLS.

Токен одноразовый и действует час. Контроллер хранит его только до использования или истечения срока, в резервные копии он не попадает. Новая команда заменяет неиспользованную.

Если на сервере был агент другой установки Node Plane, его журналы команд архивируются. Агент, принадлежащий другой активной ноде того же контроллера, отклоняется.

## Доступ к порту агента

Выбирается перед показом команды:

- **Открытый порт** (рекомендуется). Порт доступен всем, но обслуживается только клиент с сертификатом контроллера. Работает и при смене адреса контроллера, например за домашним NAT.
- **Только адрес контроллера**. Правило `ufw` пускает только адрес, с которого контроллер подключился при регистрации. Выбирайте только для статического адреса: после смены контроллер не достучится до агента, пока вы не измените правило на сервере, например `sudo ufw allow 50061/tcp comment 'Node Plane agent'`.

Если `ufw` не активен, агент файрвол не трогает; при необходимости ограничьте порт своим файрволом.

## Зачем агенту root

Агент выполняет на сервере работу, которая требует root:

- запускает контейнеры Xray и AmneziaWG через Docker; доступ к сокету Docker уже равнозначен root. Образы скачиваются по digest и получают локальные теги `node-plane-xray:<версия>` и `node-plane-awg:<версия>`; на сервере ничего не собирается. Контейнеры называются `node-plane-xray` и `node-plane-awg` и не пересекаются с отдельно установленными Xray или AmneziaWG;
- ставит Docker и системные пакеты через `apt-get` при установке сервера;
- открывает VPN-порты в `ufw`;
- ограничивает скорость через `tc` и `nft` и входит в сетевое пространство контейнера AmneziaWG через `nsenter`;
- записывает настройку IPv6 в `/etc/sysctl.d/70-node-plane-ipv6.conf`;
- управляет файлами протоколов в `/opt/node-plane-runtime`, `/etc/xray` и `/opt/amnezia/awg`;
- удаляет себя и свои ресурсы при удалении ноды.

Уже из-за Docker отдельный непривилегированный пользователь не ограничил бы возможности взломанного агента. Rootless-контейнеры не поддерживают сетевые возможности ядра, нужные AmneziaWG.

## Что контроллер может делать на сервере

Контроллер вызывает API агента: развёртывание протоколов, доступ профилей, настройки, диагностика, ограничения скорости и подключений, удаление. Изменения журналируются на сервере.

Контроллер не передаёт ничего, что агент исполняет: точки входа runtime, генератор профилей AWG и скрипт запуска контейнера AmneziaWG встроены в агент, а контроллер доставляет только данные, например `node.env`. Поэтому взломанный контроллер может только то, что позволяет API агента, если только вы не оставили на сервере ключ контроллера после **Установить по SSH**; удаление ноды этот ключ убирает. Python на сервере не нужен.

## Укрепление сервиса

Агент держит на месте `/etc/systemd/system/node-plane-agent.service.d/hardening.conf` и восстанавливает его, если файл изменили. Домашние каталоги доступны только для чтения, поэтому агент не может добавить SSH-ключ. Он не может загружать модули ядра (нужные `tc`, `nft` и Docker ядро по-прежнему загружает само), читать журнал ядра, менять cgroup и имя хоста и выполняет только системные вызовы 64-битной архитектуры. Агенты прежних версий добавляют файл при следующем запуске; действует он со следующего перезапуска, например после обновления.

Это защита от ошибок, а не от взломанного агента. Агенту нужен сокет Docker, он пишет юниты systemd для временного доступа и запускает временные юниты; любой из этих путей выводит из любой песочницы. Более строгая песочница (`ProtectSystem=strict`, урезанные capabilities) поэтому не остановила бы атакующего, но могла бы сломать Docker, apt, ufw или ограничение скорости. Взломанный контроллер ограничивают меры выше: API агента, отсутствие доставки исполняемого и подписанные релизы агента.

## Обновление агента

**Обновления** обновляют агенты вместе с контроллером. Контроллер называет свой релиз, а агент сам скачивает его с GitHub и проверяет:

- при сборке релиза подписывается заявление с версией и SHA-256 архива агента. Агент принимает только заявление, подписанное ключом релизов, который встроен в него самого, поэтому ни контроллер, ни подменённая загрузка не могут подсунуть ему другой бинарь;
- версия должна быть новее работающей, более старые релизы отклоняются;
- новый бинарь должен запуститься на этом сервере и назвать подписанную версию.

Агент сохраняет текущий бинарь как `node-plane-agent.previous`, заменяет себя и перезапускается. Перед перезапуском он заводит таймер systemd: если через три минуты новый агент не обслуживает запросы, прежний бинарь возвращается на место и сервис перезапускается. В Обновлениях будет видно, что обновление откатилось; эту версию агент сам повторять не будет. Устранив причину, выполните на сервере:

```sh
sudo node-plane-agent self-update https://github.com/saharoktyan/node-plane/releases/download/vX.Y.Z X.Y.Z
```

Агенты, выпущенные до самообновления, и агенты, собранные без ключа релизов, сами не обновляются, а по SSH контроллер агенты не обновляет: один раз переустановите такой агент новой командой установки.

## Удаление

Полное удаление сервера отзывает доступ и просит агента удалить runtime. Перед самоудалением агент проверяет сервер: runtime, `node.env`, конфиги протоколов и управляемые контейнеры должны отсутствовать. Об этом он сообщает вместе с `/etc/machine-id` сервера, который контроллер запомнил перед началом удаления. Затем агент удаляет свою службу, бинарник, конфигурацию, ключи, журналы, юниты временного доступа и SSH-ключ контроллера, если он у контроллера есть. Контроллер удаляет ноду, когда агент, сообщивший тот же machine-id, перестаёт отвечать.

Удаление самого агента не проверяется: контроллер не может заглянуть на сервер после этого, а агент, переставший отвечать по другой причине, выглядит так же. Запись о ноде и бот говорят об этом прямо. Если через десять минут агент всё ещё отвечает, удаление останавливается с `agent_still_running`; проверьте службу `node-plane-agent` на сервере. Агенты до этой проверки не сообщают machine-id; сначала обновите их. Собственную ноду контроллера после удаления по-прежнему проверяет сам контроллер.

## Файлы на сервере

| Путь | Содержимое |
|---|---|
| `/usr/local/bin/node-plane-agent` | Бинарь агента |
| `/usr/local/bin/node-plane-agent.previous` | Прежний бинарь после самообновления |
| `/etc/systemd/system/node-plane-agent.service` | Сервис |
| `/etc/systemd/system/node-plane-agent.service.d/hardening.conf` | Укрепление сервиса |
| `/etc/node-plane/agent.toml` | Ключ ноды, адрес прослушивания, пути TLS |
| `/etc/node-plane/tls/` | Ключ и сертификат агента, CA контроллера; токен до регистрации |
| `/etc/node-plane/node.env` | Настройки ноды |
| `/var/lib/node-plane-agent/` | Журналы команд, идентификатор установки контроллера, состояние самообновления в `update/` |
| `/opt/node-plane-runtime/` | Файлы протоколов и клиентские конфиги |

Полное удаление ноды удаляет агент и его ресурсы и проверяет хост. См. [Ноды](nodes.ru.md#удаление-ноды).
